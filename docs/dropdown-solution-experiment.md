# 装飾付きプルダウンの解決方法の比較

本記録は実装前の比較実験。表面クリック案は後に本体へ組み込み済み：[実装と検証結果](dropdown-surface.md)。下記の差し替え用試作スクリプトは当時のソース用であり、現在の本体では本体用の検証コマンドを使う。

2026-09-18、Brave Browser / Browser Harness で検証。今回は本体の処理を変更せず、`artifacts/dropdown-prototype/prototype.py` の一時的な差し替えで比較した。以下は採用案の検証結果であり、本体への実装完了や全サイト対応を示すものではない。

## 結論

今回のAmazonの構造には対応可能。推奨は **観測・実行で同じ操作可否判定を使い、対応関係を確認できる装飾ボタンを通常の CLICK として提示する方法**。

モデルへの新しい操作や、Amazon専用のID・CSSクラス・選択値・操作手順は不要だった。表面ボタンをクリックして再観測すると、既存の `role=option` の検出で「価格: 安い順」が現れ、その選択も既存の CLICK で実行できた。

元の依頼では並べ替え後に3mケーブルの商品ページへ進めた。ただし商品ページでの完了判定がページ変化により5回連続で無効化され、実行状態は blocked。今回の試作をエージェント全体の完走保証とは扱わない。

## 確認したDOM構造

- 背面のネイティブ select は `opacity: 0.01`、`z-index: -1`。アクセシビリティツリー上では combobox として公開される。
- 表面は `tabindex=-1`、`cursor:pointer` の span。表示ラベルは「並べ替え::おすすめ」。`aria-hidden=true` のため、通常のARIAベースの候補抽出では落ちる。
- 約10秒待ってもこの重なりは解消しなかった。

したがって、一律の待機やアクセシビリティツリーへの切り替えだけでは、この操作対象の不一致を解決できない。

## 試作の認識条件

装飾ボタンとして候補にするのは、以下をすべて満たす場合に限定した。

1. 観測した native select は接続・有効・表示状態にあるが、その位置では別要素がクリックを受ける。
2. クリックを受ける要素をたどると、select と同じ親の別の子要素になる。親が body/html の場合は対象外。
3. その表面要素に tabindex があり、cursor は pointer。表示されていて、無効・inert ではない。
4. 表面に、元の select のラベルと現在の選択肢が表示されている。
5. 表面の大きさが局所的なコントロールの範囲に収まる。

これは複数の観測事実を組み合わせた推定であり、標準仕様による対応関係の保証ではない。名前・配置が違うウィジェットは対象外となる。全画面に重なる別ダイアログや、単に近くにある要素を代わりにクリックしない。

候補には表面の実際のDOMノードを登録し、モデルにはその表示名と CLICK だけを渡す。実行時にも対応関係と現在のクリック位置を再検証する。候補はDOM順に並べてから件数制限するため、後から追加した装飾ボタンが候補上限から漏れることを避ける。

クリック位置・被覆・無効化の判定コードは観測と実行で共有した。aria-hidden を一律に無視する変更ではなく、上記条件を満たす装飾ボタンだけ、視覚的な操作対象として扱う。

## 実サイトでの比較

まず、手動で選んだ観測済みの対象を用いた比較では、次の両方でURLと選択表示が「価格: 安い順」に変わった。

- 実験限定で被覆検証を外し、native select の selectedIndex + input/change を実行。
- 表面ボタンをクリックし、再観測したメニュー項目をクリック。

被覆検証を全面的に外す方法は、依頼された「無関係な被覆では操作前に拒否する」という条件を満たさないため採用しない。

次に、サイト固有の操作をモデル外で指定せず、既存の Agent / モデル判断で比較した。

| 案 | 単独の並べ替え | 実行操作数 | TypeSafe呼び出し数 | loop時間 |
|---|---|---|---|---|
| 表面 CLICK、試行1 | URLと選択表示で成功確認 | 2 | 7 | 3,469 ms |
| 表面 CLICK、試行2 | URLと選択表示で成功確認 | 2 | 4 | 2,680 ms |
| 対応関係を確認した native SELECT、試行1 | URLと選択表示で成功確認 | 1 | 5 | 2,357 ms |
| 対応関係を確認した native SELECT、試行2 | URLと選択表示で成功確認 | 1 | 5 | 1,816 ms |

ここで比較した SELECT 案も、上記の対応関係を確認できる装飾に限って許可した。無関係な被覆は許可しない。各試行の text-model 呼び出しは0。時間は初回観測と最後の独立した読み取りを除く。各2試行の逐次比較であり、速度・成功率の一般的な優劣は主張しない。

元のGoogle開始の依頼も、それぞれ1回実行した。

| 案 | 結果 | 呼び出し数 | loop時間 |
|---|---|---|---|
| 表面 CLICK | 価格順URLへの遷移後、USB Type C・3m表記の商品 B0DCZ6GFP4 に到達。商品ページの完了判定中に blocked | TypeSafe 23 + text 1、9操作 | 13,714 ms |
| 対応確認付き SELECT | 商品 B08PZBYCW1 に到達し done。ただし SELECT 後に再検索が入り、価格順の維持は未確認 | TypeSafe 17 + text 1、6操作 | 9,183 ms |

商品到達は、終了後に新しく取得したURLとページタイトルで確認した。done 自体を成功の証拠にはしていない。商品の最安性は評価していない。

表面案では全体の実行中に、開くボタンがモデルによって3回選択された。これは通信失敗による自動再送ではないが、メニュー表示の待機・判断には改善余地がある。SELECT 案ではDOM上の選択値を変えられても、その後のアプリ側の遷移完了を待てるかが課題。イベントハンドラー未準備なのか、遷移待機が短いのかは今回の記録では特定していない。

今回は、実際に表示された選択肢を経由し、元の依頼でも価格順への遷移を確認できた表面 CLICK 案を推す。SELECT 案も不可能ではなく、アプリへの反映確認と待機を含めて設計するなら候補に残る。

## ローカル実ブラウザ検証

`uv run python artifacts/dropdown-prototype/check.py`：**13項目通過、モデル呼び出しなし**。

- 表面を1回開き、観測した選択肢を1回選べる。
- 通常の native select は引き続き操作できる。
- 全画面被覆、無関係な同階層要素、無効化、操作を示す属性の欠落では候補から除外する。
- 観測後に表面の対応関係が変わると、実行側でも拒否する。
- 比較用 SELECT 案では input/change がそれぞれ1回だけ発火する。
- 比較用 SELECT 案でも被覆・無効化を観測側と実行側の両方で拒否する。

装飾コントロールの一般性や他のサイトのJSフレームワークまで検証したものではない。ブラウザ変更・イベント再送の既存停止規則は変更していない。

## 実装する場合の範囲

1. クリック位置・無効化・被覆判定を共通関数に切り出し、観測と実行で使う。
2. 上記の対応関係を満たす装飾ボタンを、実際のDOMノードに紐づく CLICK 候補として追加する。操作できない背面 SELECT は候補に出さない。
3. メニュー表示後は既存の観測 → 判断 → CLICK を使う。固定の手順は追加しない。
4. メニューを開いた直後の状態待機と、商品到達後の過度に広い完了時freshness判定は、別途測定して改善する。全操作への固定sleepや、単なる失敗上限の引き上げで代用しない。
